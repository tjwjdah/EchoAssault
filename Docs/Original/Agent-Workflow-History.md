# Echo Assault 작업 지침

> **개발 당시 상세 문서 보관본** · 원본 파일 `AGENTS.md` · 2026-11-21 KST 개발 작업 트리 기준.
> 개발 당시 사용한 작업 지침을 열람하는 기록이다. 이 파일에는 당시의 승인 범위, 일정과 보고 규칙이 들어 있다. 공개 저장소에서 작업할 때는 연결된 현재 지침과 사용자의 최신 요청을 따른다.
> 공개 시 정리한 항목은 [익명화 기록](Redaction-Notes.md)을 참고한다. [현재 공개 저장소 지침](../../AGENTS.md)

이 폴더의 기존 Unreal C++ 프로젝트를 이어서 개발한다. 후보 선정과 프로젝트 재생성을 반복하지 않는다. 시작할 때 README.md, Docs/Design.md, Docs/Status.md와 Git 상태를 확인한다. 현재 상태의 단일 기준은 Docs/Status.md다. 날짜는 한국 시간으로 기록한다.

- 요구 우선순위: 사용자의 최신 지시 > 확정 기획 텍스트(2) > 공통 지침 텍스트(1). 선정 대기·코드 수정 금지 같은 오래된 단계 지시는 폐기한다.
- 역할 분담: Work는 일정·설계·위험·지원 자료 관리, Codex는 로컬 구현·빌드·검사·Git·상태 기록, 사용자는 중요한 판단·코드 리뷰·실제 플레이를 담당한다. 일반적인 로컬 작업은 Work의 추가 승인 없이 이어간다. 역할별 실제 수행 결과는 Docs/Status.md에 기록한다.
- 최우선은 실제 게임 완성과 취업에 활용할 실전 역량이다. 기존 일정·하네스를 유지하며 AI 활용 생산성과 일반 Unreal C++ 게임 클라이언트 채용에도 설명할 수 있는 사용자의 설계·구현·디버깅 경험을 함께 확보한다.
- 직접 C++ 구현 후보는 게임에 실제 필요한 핵심 기술·의미 있는 기능에서 선정하고 기능·취업/실력 측면의 가치·예상 난이도·일정 영향을 제안한다. 반드시 사용자 동의를 받은 뒤 사용자 담당 범위로 지정하고 Codex가 먼저 완성하지 않는다. 자연스러운 후보가 없더라도 최종 완성 전 기존 핵심 기능의 의미 있는 개선을 제안하되 형식적인 연습용 기능은 만들지 않는다.
- 사용자 담당 구현은 목표·요구사항·관련 코드·Unreal API와 힌트 안내 → 사용자 설계·C++ 작성 → Codex 리뷰 → 가능하면 사용자 우선 수정·필요 시 AI 지원 → Codex 빌드·자동 검사 → 사용자 실제 플레이 순서다. 처음부터 완성 코드를 제공하지 않으며 다른 독립 구현·검증은 계속 진행한다. 실제 직접 작성·리뷰·AI 지원 범위는 Status에 구분해 기록한다.
- 실제 편집·빌드·게임 실행 위치는 프로젝트 루트 하나다. 스크립트는 자신의 위치로 루트를 계산한다. 복사본에서 성공한 빌드를 현재 프로젝트 성공으로 대신하지 않는다.
- 완료 조건 설정 → 관련 코드 수정 → 실제 빌드·관련 검사 → 실패 분석·재수정 → 상태·근거 기록 → 다음 작업 순서다. 실패를 생략하거나 성공으로 표시하지 않는다.
- GUI 실행, 자동 검사, 사람이 실제 플레이한 결과를 구분한다. 상태는 완료 / 부분 완료 / 미완료 / 검증 불가로 기록한다.
- 11/19 실제 플레이 MVP, 11/20 테스트·지원서 초안 병행, 11/22 Windows 패키지·시연·README, 11/23 제출 목표, 11/24 23:59 KST 공식 마감이다.
- 게임은 4분 생존, 체력 0 패배, 재시작 초기화. WASD·마우스·자동 사격, 경험치·정지 중 유효 강화 3개, 공유 기록과 최대 3분신, 지연 8/16/24 → 7/15/23 → 6/14/22를 유지한다. 첫 분신은 8초 후 등장한다.
- 과거 무기 상태·발사 위치·방향을 보존하고 현재 월드에서 명중·피해를 계산한다. 이동 보간과 공격 이벤트를 분리한다. 엔진의 이동·충돌·투사체·유도를 활용한다.
- 기존 변경을 보존하고 의도한 파일만 로컬 커밋한다. 이번 작업에서 원격 생성·업로드·Push는 하지 않는다. 다른 Unreal 프로젝트를 종료하지 않는다.
- C++ 짧은 호출·조건문·선언은 한 줄로, 긴 줄만 의미 단위로 나눈다. 불필요한 프레임워크와 문서를 늘리지 않는다.
- 핵심 파일: Tools/Build.ps1, ReplayCheck.cmd, Verify.ps1; Source/EchoAssault/EchoGame.cpp, EchoActors.cpp, EchoInterface.cpp, EchoHistory.h, EchoPlayback.h.
- 사용자 판단과 AI의 구현·수치 선택을 구분한다. 실제로 측정하지 않은 성능·효율 향상은 주장하지 않는다. 사용자가 직접 할 작업은 한 번에 하나씩 구체적으로 안내한다.
- 중요한 아키텍처·게임 규칙·검증 정책 변경은 대안·추천·근거를 보여주고 사용자 판단을 받는다. 사용자가 제안하거나 학습 중 발견한 대안은 기존 방식과 실제 이점·위험을 비교하고 무조건 구현하지 않는다. 기존 의도에 맞추는 사소한 구현 선택·일반 버그 수정·반복 분석·빌드·검사·로그 정리는 자율 수행한다. 테스트를 약화해 통과시키지 않는다.
- 중요한 버그·핵심 시스템 문제는 수정 전에 실패 상황·재현 조건·C++ 파일/함수·실제 로그·핵심 코드·호출 흐름·확인 항목·일정 영향을 제공하고 사용자가 먼저 원인과 수정 방향을 추론할 기회를 준다. 직접 분석 단계에서는 원인·정답·완성 수정안을 먼저 공개하지 않고 사용자 추측을 실제 코드와 대조해 검토한다. 사용자 설명 요청 후에는 근거와 원인을 설명하고 직접 수정 또는 AI 구현으로 이어간다. 명확한 컴파일 오류·사소한 반복 수정은 자율 처리한다. 긴급하거나 개발을 막는 중요 문제는 이유를 밝히고 안전한 수정·검증을 우선한 뒤 사용자 리뷰를 진행한다.
- 보고는 사용자 질문에 먼저 답하고 결론 → 핵심 근거 → 검증 결과 → 사용자 결정 사항 순서로 작성한다. 일반 보고는 5~10줄 내외로 하며 긴 로그·반복 분석·상세 이력은 기존 문서에 보존한다. 구현·빌드·자동 검사·사람 플레이를 구분하고 간결한 보고 때문에 검증 범위·품질을 줄이지 않는다. 실패 원인·중요 설계 변경·사용자 판단 사항과 요청받은 심층 코드 설명에는 분량 제한을 적용하지 않는다.
- '이번 작업에서 읽어볼 파일과 학습 내용'은 새로운 구현·버그 수정·중요한 설계 판단이 발생했을 때만 제공한다. 코드 변경 없는 단순 QA·빌드·테스트 실행·문서 갱신에는 학습 코드나 질문을 억지로 붙이지 않는다. 코드 변경이 없어도 중요한 문제·설계 위험을 발견하면 보고한다. 학습 안내는 파일 1개의 정확한 경로·관련 함수/섹션·역할·이번 작업과의 관계, 핵심 코드/스크립트 1~2개와 실행 흐름·사용 예시로 설명한다. 프로젝트 핵심 알고리즘·설계 판단, Unreal 내부 동작과 객체 수명·프레임/Tick·충돌·입력의 실제 문제, 버그 재현·원인·수정·검증, 대안의 성능·안정성 트레이드오프, AI 코드의 중요 검토 지점을 우선한다. 실제 코드에 근거한 생각할 가치가 있는 질문만 제시하고 적절한 질문이 없으면 생략한다. 핵심 수정은 변경 전후·이유·대안을 짚고 테스트 조건 제안이나 설계 판단의 기회를 준다. 틀린 이해는 근거로 교정하고 추측은 사실과 구분한다. 사용자 답변·실행 전에는 리뷰 참여 완료로 기록하지 않는다.
- 기본 파일 학습 순서는 README.md → AGENTS.md → Docs/Status.md → Tools/Verify.ps1 → Docs/Design.md → Tools/Build.ps1 → Tools/ReplayCheck.cmd다. 실제 개발 관련 파일은 먼저 설명할 수 있다. 사용자는 C++·Unreal 기본 게임 개발 경험이 있으므로 기초 문법·일반적인 구현 이유를 반복 질문하지 않고, 기초 개념은 사용자가 질문할 때 설명한다. 하네스·Codex 운영·PowerShell·테스트 환경은 초보 수준을 고려해 실제 작업과 연결하되 파일 전체 암기·문법 숙달을 요구하지 않는다. 개발 속도를 유지하며 게임 클라이언트 프로그래머의 실전 역량을 우선한다.
- 학습 안내·이해 확인은 Status에만 기록하며 사용자가 실제로 읽고 이해했다고 확인한 내용만 완료 처리한다. 이해가 확인된 내용은 반복하지 않고 추가 질문을 받을 수 있게 안내한다. 학습 응답을 일반 구현·검증의 대기 조건으로 삼지 않아 11/19 MVP·11/22 완성 일정을 우선한다. 별도 학습 시스템·문서를 만들지 않는다.
- 주요 작업은 문제·완료 조건, 설계·구현, 사용자 검토, 실제 검증, 역할별 기여와 근거, 다음 작업을 남긴다. 현재 상태는 Status 하나에만 갱신하고 운영 설명은 README, 설계 이유는 Design에 둔다.
- 매일 시작 시 KST 날짜·마감까지 남은 일정, 필수/권장/여유 작업, 완료 조건·검증 방법, 완료/남은 항목을 Status의 당일 계획에서 확인한다. 의미 있는 작업 하나가 끝날 때마다 별도 요청 없이 위 보고 순서에 맞춰 당일 완료 수/전체 수·달성률, MVP/최종 체크리스트 수, 남은 일·최대 위험, 다음 한 단계·역할별 참여를 짧게 보고하고 Status를 갱신한다. 사람이 확인할 플레이는 구체적인 실행 방법과 기대 결과를 안내한다.
- 진척도는 명시한 체크리스트의 실제 완료 항목만 집계한다. 작성·빌드·자동 검사·사람 플레이를 구분하고 부분 완료/검증 대기는 완료 수에 넣지 않는다. 개수 기반 합격률을 공수·전체 개발 완성도 추정으로 표현하지 않는다. 분모·완료 기준을 바꾸면 이유와 전후 수치를 남긴다. 당일 목표가 위험하면 필수 유지 기능·미룰 항목·AI 추가 작업·회복안을 즉시 제시한다. 문서·코드 작성량을 성과로 삼지 않고 플레이 가능한 게임·검증된 동작·사용자의 기술적 이해와 실제 기여를 우선한다.
